# Coding Agent for Slack (Bolt for Python and OpenAI Agents SDK)

A sample Slack **coding agent** built with [Bolt for Python](https://docs.slack.dev/tools/bolt-python/) and [OpenAI Agents SDK](https://openai.github.io/openai-agents-python/) using models from [OpenAI](https://openai.com). When you mention the agent, it decides whether to reply in place or create a dedicated **code channel** for the work. In a code channel it clones a repository into a temp workspace, does real work there, and keeps the channel's plan, context bar, and code tab current as it goes.

> [!WARNING]
> **This agent runs shell commands generated by a language model on the machine running the app.** Commands outside a small read/test allowlist require your approval in Slack before they run (see [Command approvals](#command-approvals)), but approval is the real safety gate, not the allowlist — a shell is expressive (pipes, `&&`, subshells) and the allowlist only checks the first token. **Only run this sample against trusted, throwaway repositories, and on a machine you're comfortable letting it operate.** It is a reference sample, not a hardened product.

## App Overview

The coding agent works like this:

1. You `@Coding Agent fix the flaky login test in <repo>` in any channel.
2. The agent decides how to handle it. A question gets an answer in the thread. Work that takes more than one message gets a code channel, created with the `create_code_channel` tool and linked back to your message.
3. Slack seeds the new channel with your request, mention included, and that mention starts the session there. The agent clones the repo, pins it to the context bar, writes a plan, and registers a few slash commands for the channel.
4. It makes changes with `run_command`. Safe commands (`ls`, `grep`, `pytest`, `git diff`, …) run immediately; anything else asks for your approval first.
5. It publishes the diff to the code tab and summarizes what it did.
6. Keep chatting in the channel (no `@`-mention needed), comment on the plan, or use its slash commands to iterate.
7. When you say it's done, the agent posts a summary, which is shared back to your original message, and archives the channel.

### Tools

Each code channel method is a tool the model calls when it decides to, in [`agent/tools/`](./agent/tools/), one file per tool:

| Tool | Method |
| --- | --- |
| `create_code_channel` | `agents.conversations.create` |
| `set_context_bar` | `agents.conversations.setProperties` |
| `publish_diff` | `agents.conversations.setView` (`diff`) |
| `publish_html_view` | `agents.conversations.setView` (`html`) |
| `write_plan` | `canvases.create` + `agents.conversations.setView` (`canvas`), then `agents.conversations.setCanvasContent` |
| `read_plan` | `agents.conversations.getCanvas` |
| `list_views` | `agents.conversations.listViews` |
| `remove_view` | `agents.conversations.removeView` |
| `set_commands` | `agents.conversations.setCommands` |
| `rename_session` | `agents.sessions.rename` |
| `archive_channel` | `chat.postMessage` + `agents.sessions.setStatus` (`closed`) + `agents.conversations.archive` |
| `clone_repo` | Local `git clone` into a temp directory |
| `run_command` | Local shell in that directory |

`create_code_channel` is the only tool when answering a mention outside a code channel, and the one tool missing inside it, so the agent can't create a channel from a channel. The session status belongs to the session lifecycle rather than the model, so the listeners call `agents.sessions.setStatus` around every turn (`processing` while working, `suspended` while waiting on an approval, `active` when done). Wrapping up is the exception: `archive_channel` sets `closed` itself, right before it archives the channel.

### Code channel behavior

- **Plan as a canvas.** The plan is attached with comment access, so people can comment but only the agent edits. `read_plan` gives the agent open comments each turn, and `setCanvasContent` keeps comments anchored to the sections it didn't change.
- **Agent slash commands.** Commands registered with `set_commands` arrive as slash commands. One catch-all listener ([`listeners/commands/`](./listeners/commands/)) turns `/run-tests unit` into a turn, so the agent decides what each command does.
- **Stop button.** On `agent_session_stopped`, the app drops any pending approval and flags the session so the in-flight run posts nothing more. It doesn't post or set a status after a stop, because Slack handles that.
- **Archiving from Slack.** On `channel_archive` or `group_archive`, the app forgets the session and deletes its working directory, the same cleanup `archive_channel` does when the agent wraps up.
- **Picking up code channels.** A mention in a code channel the app has no state for, whether the seeded request in a channel the agent just created, one started from Slack's UI, or one forgotten after a restart, is recognized with `conversations.info` (`properties.record_channel.record_type == "agent_channel"`) and picked up as a session.
- **Creating a channel is the agent's call.** The prompt in [`agent/agent.py`](./agent/agent.py) follows Slack's guidance: create a channel for multi-step work like changing code or running tests, and reply in place for anything that fits in one message.
- **Idempotent creation.** `create_code_channel` takes only a title. Its `session_id` comes from the triggering message, so a repeated call or a retried event reuses the same channel. The first turn only ever starts from the seeded mention, so it runs once.

### Command approvals

`run_command` is registered with the OpenAI Agents SDK's `needs_approval` hook ([`agent/approvals.py`](./agent/approvals.py)):

- **Allowlisted** read/inspect/build/test commands run with no prompt.
- **Anything else** pauses the run. The app posts Approve / Deny buttons in the code channel; your click resumes the agent with the decision. The paused run is parked in memory with its channel and the ts of the approval message, so a click only resumes the run its buttons were posted for, and buttons left over from a replaced run show as expired. That's fine for a single-instance sample. A multi-instance deployment would persist `RunState` to a shared store instead.

#### Create Your Slack App

1. Open [https://api.slack.com/apps/new](https://api.slack.com/apps/new) and choose "From an app manifest"
2. Choose the workspace you want to install the application to
3. Copy the contents of [manifest.json](./manifest.json) into the text box that says `*Paste your manifest code here*` (within the JSON tab) and click _Next_

5. Click _Install to Workspace_ and _Allow_ on the screen that follows. You'll then be redirected to the App Configuration dashboard.

#### Environment Variables

Before you can run the app, you'll need to store some environment variables.

1. Rename `.env.sample` to `.env`.
2. Open your apps setting page from [this list](https://api.slack.com/apps), click _OAuth & Permissions_ in the left hand menu, then copy the _Bot User OAuth Token_ into your `.env` file under `SLACK_BOT_TOKEN`.

```sh
SLACK_BOT_TOKEN=YOUR_SLACK_BOT_TOKEN
```

3. Click _Basic Information_ from the left hand menu and follow the steps in the _App-Level Tokens_ section to create an app-level token with the `connections:write` scope. Copy that token into your `.env` as `SLACK_APP_TOKEN`.

```sh
SLACK_APP_TOKEN=YOUR_SLACK_APP_TOKEN
```

```sh
git clone https://github.com/slack-samples/bolt-python-coding-agent.git my-coding-agent
```

### Using the App

Once the agent is running, invite it to a channel by typing `/invite @agent-name` in the message box.

**Channel @mentions** — @mention the agent with a question, like _what does this repo do?_, and it answers in a thread. @mention it with a task and a repo, like _add a "hello world" to the README of `<repo>`_, and it replies with a link to a new code channel for the work.

**Code channels** — Follow the work in the new channel. Approve or deny commands as they come up, comment on the Plan tab, review the diff in the code tab, and send follow-ups without an @mention. Say you're done to wrap up and archive the channel.

**App Home** — Open the agent in Slack and click the _Home_ tab to see how to start a task.

## Project Structure

### `manifest.json`

`manifest.json` is a configuration for Slack apps. With a manifest, you can create an app with a pre-defined configuration, or adjust the configuration of an existing app.

The app requests `code_channels:manage` for the `agents.conversations.*` methods, `chat:write` for `agents.sessions.*` and replies, `canvases:write` for the plan, `channels:read` / `groups:read` to recognize code channels and hear when they're archived, plus `app_mentions:read` and `channels:history` / `groups:history` to receive mentions and messages.

### `app.py`

`app.py` is the entry point for the application and is the file you'll run to start the server. This project aims to keep this file as thin as possible, primarily using it as a way to route inbound requests. It uses Socket Mode, so agent slash commands are routed to it without a `slash_command_url`.

### `app_oauth.py`

`app_oauth.py` is an alternative entry point that runs the app in HTTP mode instead of Socket Mode. This is intended for deployments that use OAuth for app distribution. See the OAuth HTTP Server section under Development for setup instructions.

### `/listeners`

Every incoming request is routed to a "listener". This directory groups each listener based on the Slack Platform feature used.

**`/listeners/events`** — Handles incoming events:

- `agent_session_stopped.py` — Stops the session when the stop button is pressed.
- `app_home_opened.py` — Publishes the App Home view with how to start a task.
- `app_mentioned.py` — Answers a mention in place or hands it to a code channel, and runs turns for mentions inside one.
- `channel_archive.py` — Forgets a code channel archived from Slack.
- `message.py` — Runs a turn for messages in a code channel.

**`/listeners/actions`** — Handles interactive components:

- `approval_buttons.py` — Resumes a paused run when Approve or Deny is clicked.

**`/listeners/commands`** — Handles slash commands:

- `agent_command.py` — Turns any command the agent registered into a turn.

### `/agent`

The `agent.py` file defines the routing agent and the coding agent with their prompts and tools, and runs each turn: it sets the session status, runs the agent, and posts the outcome or the Approve / Deny buttons.

The `deps.py` file defines the `AgentDeps` and `RequestDeps` dataclasses passed to the agents at runtime, providing access to the Slack client and the session or request.

The `store.py` file keeps each code channel's session in memory: its working directory, plan canvas, and conversation history.

The `approvals.py` file decides which commands need approval and holds runs paused on one.

The `tools` directory contains one file per tool the agents can call.
