# Coding Agent for Slack (Bolt for Python and Claude Agent SDK)

A sample Slack **coding agent** built with [Bolt for Python](https://docs.slack.dev/tools/bolt-python/) and the [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview) using models from [Anthropic](https://www.anthropic.com). When you mention the agent, it decides whether to reply in place or create a dedicated **code channel** for the work. In a code channel it clones a repository into a temp workspace, does real work there, and keeps the channel's plan, context bar, and code tab current as it goes.

> [!WARNING]
> **This agent runs commands generated by a language model on the machine running the app.** Only read-only commands and local git changes run without asking. Everything else, including the repo's own tests and builds, needs approval in Slack before it runs (see [Command approvals](#command-approvals)), and anyone in the code channel can approve. Approval is the safety gate, so read each command before you approve it. Commands run without the app's tokens or anything that looks like a credential in their environment. **Only run this sample against trusted, throwaway repositories, and on a machine you're comfortable letting it operate.** It is a reference sample, not a hardened product.

## App Overview

The coding agent works like this:

1. You `@Coding Agent fix the flaky login test in <repo>` in any channel, or send the agent a direct message.
2. The agent decides how to handle it, reading the thread or direct message the request came from. A question gets an answer in place. Work that takes more than one message gets a code channel, created with the `create_code_channel` tool and linked back to your message.
3. Slack seeds the new channel with your request, mention included, and that mention starts the session there, along with the conversation the request came from. The agent clones the repo, pins it to the context bar, writes a plan, and registers a few slash commands for the channel.
4. It reads and edits files with `read_file`, `edit_file`, and `write_file`, which stay inside the clone and never ask. It runs commands with `run_command`: read-only commands (`ls`, `grep`, `git diff`, …) and local git changes (`git switch -c`, `git commit`, …) run immediately; anything else, including tests, asks for your approval first.
5. It publishes the diff to the code tab and summarizes what it did.
6. Keep chatting in the channel (no `@`-mention needed), comment on the plan, or use its slash commands to iterate. Messages sent while the agent works go into its next turn together.
7. When you say it's done, the agent posts a summary, which is shared back to your original message, and archives the channel.

### Tools

Each code channel method is a tool the model calls when it decides to, in [`agent/tools/`](./agent/tools/), one file per tool. The tools are served to the model by an in-process MCP server, so it sees each one as `mcp__coding-agent__<name>`:

| Tool | Method |
| --- | --- |
| `create_code_channel` | `agents.conversations.create` |
| `set_context_bar` | `agents.conversations.setProperties` |
| `publish_diff` | `agents.conversations.setView` (`diff`) |
| `publish_html_view` | `agents.conversations.setView` (`html`) |
| `write_plan` | `canvases.create` + `agents.conversations.setView` (`canvas`), then `agents.conversations.setCanvasContent` |
| `read_plan` | `agents.conversations.getCanvas` |
| `list_views` | `agents.conversations.listViews` |
| `remove_view` | `agents.conversations.removeView` |
| `set_commands` | `agents.conversations.setCommands` |
| `rename_session` | `agents.sessions.rename` |
| `archive_channel` | `chat.postMessage` + `agents.sessions.setStatus` (`closed`) + `agents.conversations.archive` |
| `clone_repo` | Local `git clone` into a temp directory |
| `read_file`, `write_file`, `edit_file` | Local files in that directory |
| `run_command` | A local program in that directory, run without a shell |

`create_code_channel` is the only tool when answering a mention outside a code channel, and the one tool missing inside it, so the agent can't create a channel from a channel. The session status belongs to the session lifecycle rather than the model, so the listeners call `agents.sessions.setStatus` around every turn (`processing` while working, `suspended` while waiting on an approval, `active` when done). Wrapping up is the exception: `archive_channel` sets `closed` itself, right before it archives the channel.

### Code channel behavior

- **Plan as a canvas.** The plan is attached with comment access, so people can comment but only the agent edits. `read_plan` gives the agent open comments each turn, and `setCanvasContent` keeps comments anchored to the sections it didn't change.
- **Agent slash commands.** Commands registered with `set_commands` arrive as slash commands. One catch-all listener ([`listeners/commands/`](./listeners/commands/)) turns `/run-tests unit` into a turn, so the agent decides what each command does.
- **Stop button.** On `agent_session_stopped`, the app flags the session so the in-flight run calls no more tools and posts nothing more, replaces any pending Approve / Deny buttons so they can't resume it, confirms the stop in the channel, and sets the session to `active`. Slack doesn't change the status on a stop, so the app has to.
- **Archiving from Slack.** On `channel_archive` or `group_archive`, the app forgets the session and deletes its working directory, the same cleanup `archive_channel` does when the agent wraps up.
- **Picking up code channels.** A message, mention, or slash command in a code channel the app has no state for, whether the seeded request in a channel the agent just created, one started from Slack's UI, or one forgotten after a restart, is recognized with `conversations.info` (`properties.record_channel.record_type == "agent_channel"`) and picked up as a session. Other channels are looked up once and remembered.
- **The conversation comes along.** A new session reads the thread or direct message its channel was started from (`properties.agent_session.origin_link`) and gives it to the agent's first turn, so a request like "fix this" keeps its context.
- **One turn at a time.** Messages that arrive while the agent works wait, and go into its next turn together, each labeled with who sent it. The stop button drops them along with the turn.
- **Creating a channel is the agent's call.** The prompt in [`agent/prompts.py`](./agent/prompts.py) follows Slack's guidance: create a channel for multi-step work like changing code or running tests, and reply in place for anything that fits in one message.
- **Idempotent creation.** `create_code_channel` takes only a title. Its `session_id` comes from the triggering message, so a repeated call or a retried event reuses the same channel. The first turn only ever starts from the seeded mention, so it runs once.

### Command approvals

Every tool call the coding agent makes goes through a Claude Agent SDK `PreToolUse` hook ([`agent/guardrails.py`](./agent/guardrails.py)), and for `run_command` it asks `command_needs_approval` in [`agent/approvals.py`](./agent/approvals.py):

- **Read-only** commands like `ls`, `grep`, and `git diff`, and **local git changes** like `git add`, `git commit`, and `git switch -c`, run with no prompt. A path outside the clone, like `/etc`, `C:\Windows`, or `../x`, always asks. Commands run without a shell on every platform, so `&&`, `|`, `>`, and `$(...)` reach the program as plain text and can't chain a second command, and what the approval check reads is exactly what runs.
- **File edits** don't go through approvals. `write_file` and `edit_file` only write inside the clone, and never into `.git`, whose config and hooks decide what git runs.
- **Anything else** pauses the run. The hook defers the call, which ends the run with the call waiting, and the app posts Approve / Deny buttons in the code channel. Your click resumes the Claude Code session, and the hook answers the waiting call with your decision. The paused run is parked in memory with its channel and the ts of the approval message, so a click only resumes the run its buttons were posted for, and buttons left over from a replaced or stopped run show as expired. Sending a new message while an approval is pending skips that command: the next turn answers it as not run before reading your message. That's fine for a single-instance sample. A multi-instance deployment would keep the paused runs, and the Claude Code session transcripts, in a shared store instead.

The agent gets only these tools. Claude Code's built-in tools, like its own `Bash` and `Edit`, are turned off, and so are the settings, `CLAUDE.md` files, and MCP servers configured on the machine running the app.

## Providers

### Anthropic Setup

This app uses Claude through the Claude Agent SDK: `claude-sonnet-5-5` for the coding agent and `claude-haiku-4-5` for deciding whether a request needs a code channel.

1. Create an API key from your [Anthropic dashboard](https://console.anthropic.com/settings/keys).
2. Rename `.env.sample` to `.env`, if you haven't already.
3. Save the Anthropic API key to `.env`:

```sh
ANTHROPIC_API_KEY=YOUR_ANTHROPIC_API_KEY
```

The Claude Agent SDK runs the Claude Code CLI that comes bundled with it, and the CLI keeps each session's conversation as a transcript under `~/.claude/projects/`, including tool inputs and outputs like file contents and command output. Follow-up turns resume from that transcript.

### Using the App

Once the agent is running, invite it to a channel by typing `/invite @agent-name` in the message box.

**Channel @mentions** — @mention the agent in a thread with a question about the conversation, like _what did we decide here?_, and it answers in the thread. @mention it with a task and a repo, like _add a "hello world" to the README of `<repo>`_, and it replies with a link to a new code channel for the work.

**Direct messages** — Open the agent's _Messages_ tab and ask a question or describe a task, or pick a suggested prompt. It answers there, or links a code channel for bigger work.

**Code channels** — Follow the work in the new channel. Approve or deny commands as they come up, comment on the Plan tab, review the diff in the code tab, and send follow-ups without an @mention. Say you're done to wrap up and archive the channel.

**App Home** — Open the agent in Slack and click the _Home_ tab to see how to start a task.

## Project Structure

### `manifest.json`

`manifest.json` is a configuration for Slack apps. With a manifest, you can create an app with a pre-defined configuration, or adjust the configuration of an existing app.

The app requests `code_channels:manage` for the `agents.conversations.*` methods, `chat:write` for `agents.sessions.*` and replies, `canvases:write` for the plan, and `channels:read` / `groups:read` to recognize code channels and hear when they're archived. It receives mentions with `app_mentions:read` and messages with `channels:history` / `groups:history` / `im:history`, and those history scopes plus `mpim:history` let it read the thread or direct message a request came from. `assistant:write`, `im:read`, and `im:write` support the agent's direct-message experience under `agent_view`.

### `app.py`

`app.py` is the entry point for the application and is the file you'll run to start the server. This project aims to keep this file as thin as possible, primarily using it as a way to route inbound requests. It runs Bolt's `AsyncApp` in Socket Mode, so a long agent turn never holds up the stop button, an approval click, or another channel, and agent slash commands are routed to it without a `slash_command_url`.

### `app_oauth.py`

`app_oauth.py` is an alternative entry point that runs the app in HTTP mode instead of Socket Mode. This is intended for deployments that use OAuth for app distribution. See the OAuth HTTP Server section under Development for setup instructions.

### `/listeners`

Every incoming request is routed to a "listener". This directory groups each listener based on the Slack Platform feature used.

**`/listeners/events`** — Handles incoming events:

- `agent_session_stopped.py` — Stops the session when the stop button is pressed.
- `app_home_opened.py` — Publishes the App Home view with how to start a task.
- `app_mentioned.py` — Answers a mention in place or hands it to a code channel, and runs turns for mentions inside one.
- `channel_archive.py` — Forgets a code channel archived from Slack.
- `message.py` — Answers direct messages like mentions, and runs a turn for messages in a code channel.

**`/listeners/actions`** — Handles interactive components:

- `approval_buttons.py` — Resumes a paused run when Approve or Deny is clicked.

**`/listeners/commands`** — Handles slash commands:

- `agent_command.py` — Turns any command the agent registered into a turn.

### `/agent`

The `agent.py` file defines the routing agent and the coding agent with their tools, and starts and resumes their runs. Along with `guardrails.py` and `tools`, it's the only code that uses the Claude Agent SDK.

The `prompts.py` file holds both agents' prompts.

The `turns.py` file runs each turn for the listeners: it answers requests, sets the session status, runs the agent, and posts the outcome or the Approve / Deny buttons. It also queues messages that arrive mid-turn and handles approvals and the stop button.

The `outcome.py` file defines the `RunOutcome` that `agent.py` returns and `turns.py` reads.

The `context.py` file reads the thread or direct message a request came from, so the agent can follow the conversation.

The `guardrails.py` file holds the SDK hooks that gate tool calls: the approval check for `run_command`, which defers a command that needs approval, and the check that skips every tool call once the session is stopped.

The `sessions.py` file keeps each code channel's session in memory: its working directory, plan canvas, conversation history, and messages waiting for the next turn. It also defines the `AgentDeps` and `RequestDeps` dataclasses passed to the agents at runtime, providing access to the Slack client and the session or request.

The `approvals.py` file decides which commands need approval and holds runs paused on one.

The `runtime.py` file holds what the tools and hooks share during a run: its deps, which the SDK can't pass to a tool, and the shape of a tool's reply.

The `workspace.py` file runs commands in the clone without the app's secrets, and keeps file tools inside it.

The `tools` directory contains one file per tool the agents can call.
